# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

WriterStudio (branded "Storia" in the newer app) is a screenwriting/story-planning tool. The repo holds independent npm projects, each with its own `node_modules` and lockfile; run commands from inside each one. The root `package.json` only holds scripts: `npm run check` type-checks, lints and tests all three projects, so run it after changing `packages/core`.

- **`web-new/`**: the app (Vite + React 18 + TypeScript + Tailwind + Firebase) and its landing page. Almost all current work happens here. It replaced a legacy Create React App + Electron app and a 2022 marketing site (`website/`), which was removed from the repo once its remaining features (the story-planning boards, the terms and the privacy policy) had moved over; its Firestore data was left where it was, not imported.
- **`packages/core/`**: `@storia/core`, the UI-free code both apps share: the screenplay rules and data (`screenplay/`: types, flow, characters, pages, structure, fountain, content, cast), the board logic (`board/board.ts`), the data shapes (`datatypes/`) and `misc/randomString`. Each app depends on it as `file:../packages/core` (a link in its `node_modules`, not npm workspaces, so web-new's React 18 and mobile's React 19 never share a hoisted tree) and imports it by path, like `@storia/core/screenplay/flow`, through the package's `./*` export of its TypeScript source; nothing is built or published. Its tsconfig leaves out the DOM library, so code that needs a browser API (`DOMParser`, `DecompressionStream`, ProseMirror, React) stays in web-new: that's why `finalDraft.ts`, `writerDuet.ts`, `revisions.ts`, `describe.ts` and `board/body.ts` are still there. `npm run check` there type-checks it and runs its tests. Vite serves it in dev through `server.fs.allow` in `vite.config.ts`, and Metro through `watchFolders` in `mobile/metro.config.js`.
- `mobile/`: the native app (`storia-mobile`), just started: Expo SDK 58 with Expo Router, routes in `src/app/`. Its own `AGENTS.md` (read through `mobile/CLAUDE.md`) covers Expo's conventions: add packages with `npx expo install`, and never edit the generated `ios/` and `android/`. Check it with `npm run typecheck`, `npx expo lint` and `npm test` (Vitest, for the pure logic in `src/script/`); run it with `npx expo start`, and judge speed only with `npx expo start --no-dev --minify`: Expo Go's development build is several times slower, enough to make Return in the editor feel laggy when the production build is fine. It patches React Native (`patches/`, applied by `patch-package` on every install): on iOS, a focused field's keyboard doesn't follow a change of capitals, autocorrection or spell checking (a line becoming a cue) until the field is refocused (`reloadInputViews` isn't enough), so the patch has the field resign and retake first responder at once, keeping its selection and sending JS no blur or focus. iOS builds therefore compile React Native from source (`buildReactNativeFromSource` in `app.json`), so the patch only shows in a development build (`npx expo run:ios --device`), never in Expo Go; regenerate it with `npx patch-package react-native` after a React Native upgrade, and drop it once React Native ships the fix. The bundle identifier and Android package are `dev.russal.storia`. It takes the script's rules from `@storia/core`, so a change to them reaches both apps. For now the app opens on a block editor spike (`src/script/`): one native `TextInput` per block in a `FlatList`, with `blocks.ts` applying `flow.ts`'s Enter, Backspace and Tab between fields, an element bar above the keyboard, and a generated 120-page sample script held in memory, not saved. It replaced a 2022 prototype, which is in git history.

## Commands (`web-new/`)

```sh
npm run emulators # local Auth, Firestore and Realtime Database (needs Java 21+); start it first
npm run dev      # Vite dev server, on the emulators
npm run dev:live # Vite dev server on the real project: writers' data, so only on purpose
npm run emulators:lan # the emulators, reachable from this network (a phone on the same Wi-Fi)
npm run dev:lan  # Vite dev server on this network too, on the LAN emulators: open the Network address it prints
npm run build    # tsc type-check, then vite build -> dist/
npm run lint     # eslint, --max-warnings 0 (any warning fails)
npm run preview  # serve the built dist/
npm test         # vitest: the pure screenplay and board logic, and the editor's document (happy-dom for DOM tests)
```

`script-writer-studio` is the one Firebase project, and it is production: its console name said "Test" for historical reasons. A dev build connects to the emulators (`usesEmulators` in `firebase/main.tsx`; App Check and Analytics are skipped there), so local work never touches writers' data. The emulators load `database.rules.json`, so the rules are exercised locally too, and save to the gitignored `.emulator-data/` on Ctrl+C and load it on the next start. Make an account through the app's sign-up; it exists only in the emulator. `npm run dev:live` (`.env.live` sets `VITE_FIREBASE=live`) points a dev build at production when you really need real data. A production build always uses the real project, and the emulator code is left out of it. To try the app on a phone, run `npm run emulators:lan` and `npm run dev:lan` together (in place of the plain pair; both use the same ports). `scripts/emulators-lan.mjs` binds the emulators to this machine's LAN address, not 0.0.0.0, because the Realtime Database emulator tells clients to reconnect to the host it is bound to; it writes that config to the gitignored `firebase.lan.local.json` from `firebase.json` on each run, and `vite.config.ts` finds the same address and hands it to the app as `__EMULATOR_HOST__`. Anyone on the network can reach the emulators meanwhile, so use it on a network you trust. There's no LAN mode for the live project: App Check's reCAPTCHA key doesn't accept a bare IP. `aria-storia` is an older, unused Firebase project.

Tests sit beside the code they cover (`*.test.ts`). Use `npm run build` as the type-check gate, and `npm test` for anything in `src/screenplay/` or `src/board/`. The shared rules' and board's own tests live with them in `packages/core`.

Deploying uses Firebase Hosting: the hosting site is `new-storia` in project `script-writer-studio`, served from `dist/` with an SPA rewrite to `/app.html`. Vite builds two pages: `index.html` is the landing page at `/`, static HTML with the world's CSS (`src/landing/`) and none of the app, so it paints at once and reads to search engines and link previews; `app.html` is the app, with the boot skeleton, and every other path loads it (the dev and preview servers route the same way, through `appRoutes` in `vite.config.ts`). The landing page sends a writer signed in on that browser straight to `/home`, through the `signedIn` hint in `localStorage` that `markSignedIn` (`misc/session.ts`) keeps; the app's own `/` route only redirects to Log in, and links to the landing page are plain `<a href="/">`, not router links. Realtime Database rules live in `web-new/database.rules.json` (owner-only access) and deploy with `npx firebase-tools deploy --only database`. When you add a new RTDB path or query, update the rules to match. Each owner-only `.write` also allows deleting a node that doesn't exist, so a multi-path delete holding a stale summary's path doesn't fail as a whole. `firebase.json` serves the hashed JS and CSS as immutable and everything else (`index.html`, `version.json`, every route) as `no-cache`, so a reload always reaches the latest deploy.

## Versions and releases

`web-new` is published as `storia-web`, versioned in its `package.json` (semver, 0.x while in beta), with each release in `web-new/CHANGELOG.md` and tagged `storia-web@<version>`. `vite.config.ts` builds the version, the short commit hash and the build time into the app (`__APP_VERSION__`, `__APP_COMMIT__`, `__APP_BUILT_AT__`, read through `misc/version.ts`) and writes them to `dist/version.json`. The account menu shows "Version 0.1.0 · a1b2c3d". `UpdatePrompt`, mounted in `App.tsx`, polls `version.json` every 10 minutes and whenever the tab comes back into view, and offers a reload when the deployed build differs from the running one.

Add user-facing changes under "Unreleased" in the changelog as they land. To release, from `web-new/`:

1. `npm version <patch|minor> --no-git-tag-version` (updates `package.json` and the lockfile).
2. Rename "Unreleased" in `CHANGELOG.md` to the new version and date, and open a fresh "Unreleased" above it.
3. Commit as `web: storia-web <version>`, then `git tag storia-web@<version>`.
4. Build and deploy from that commit (`npm run build`, then `npx firebase-tools deploy --only hosting`), so the hash in the app matches the tag.

## Required gitignored files

`web-new/src/firebase/keys.tsx` (exports `APISiteKey`, the reCAPTCHA v3 key for App Check) and `web-new/src/firebase/config.tsx` (exports `firebaseConfig`, the `script-writer-studio` web config) are gitignored, and the app won't build without them. Never commit them. `web-new/.env.production.local` (gitignored by `*.local`) sets `VITE_SENTRY_DSN`; a production build without it builds fine but reports no errors. The same file holds `SENTRY_AUTH_TOKEN`, a Sentry organization token: with it, `vite.config.ts` has `@sentry/bundler-plugins` upload the build's source maps to the `storia-web` project, under the release the app reports, and then delete them from `dist/` so they're never deployed. Without it the build makes no source maps and warns that stack traces will be minified. A CI build would need the token as a secret.

## web-new architecture

**Errors:** a production build built with `VITE_SENTRY_DSN` reports to Sentry (`misc/monitoring.ts`); a dev build never does. `startMonitoring` runs in `main.tsx` before the app renders, and Sentry's default integrations catch uncaught errors and unhandled rejections themselves. The app sits inside Sentry's `ErrorBoundary`, which shows `CrashScreen` when a screen throws while drawing. For an error the app catches and carries on from, call `logError(where, error)`: it logs to the console everywhere and reports from production, tagged with `where`. `saveDocumentContent` and `changeBoard` call it themselves, so their callers don't need to. To show a caught error to the writer, pass it through `toMessage` (`misc/errors.ts`). Reports carry the writer's uid (`monitorUser`, kept in step with Firebase Auth) and no IP address, cookies, headers, bodies, local variables or console breadcrumbs (`dataCollection` and `beforeBreadcrumb`), since any of these could hold a writer's script; keep it that way, and update the privacy policy's Error Reports section if what's sent changes.

**Two Firebase databases, used for different things:**
- **Firestore** (`db`) stores only user profiles in the `users/{uid}` collection (`addUser`, `getUser`).
- **Realtime Database** (`rtdb`) stores all content in four top-level paths: `folders/`, `projects/`, `documents/`, and `boards/` (one per project, keyed by the project's id).

**Denormalised writes:** a child is written to its own path *and* copied as a summary into its parent. For example, `writeProjectData` writes `projects/{id}` and also `folders/{folderId}/projects/{id}` = `{id, name, type}`, then bumps the folder's `lastUpdated`. `writeDocumentData` does the same into `projects/{projectId}/documents/{id}`. When you add a rename, move, or delete, update both copies, in one multi-path `update(ref(rtdb), {...})` so they can't drift apart; `updateFolderDetails`, `deleteFolder` (which keeps the folder's projects, clearing their `folderId`, or with `withProjects` deletes them, their documents and their boards; pass the projects that name the folder), `updateProjectDetails` (name, description and folder; a move takes the summary out of one folder and into the other), `updateDocumentDetails` (name, description and project; a move takes the summary out of one project and into the other), `deleteProject` (which also deletes every document listed in it, and its board) and `deleteDocument` do this. Editing details doesn't bump `lastUpdated`, which tracks writing. Ownership lookups are RTDB queries on `orderByChild('owner')` or `orderByChild('folderId')`.

**Data access** lives in `src/firebase/database.tsx`. It returns refs and queries, not data. Views subscribe themselves with `onValue(ref, onData, onError)` inside a `useEffect` and return the unsubscribe function. Every view handles loading (`Loading`, which offers a retry after 12s), error, and not-found states (`LoadError`). Home, folder and project views start from what the tab last saw (`misc/seen.ts`, an in-memory cache that home's lists also feed) and remember each snapshot they receive, so a screen usually draws its content on the first frame. A new subscription on those screens should do the same. The data shapes are in `@storia/core/datatypes/` (`packages/core/src/datatypes/`), where `Block.ts` holds the `BasicBlock`/`Folder`/`Project` hierarchy.

**Screenplay documents:** every document is a screenplay. Its `content` is an array of `ScriptBlock` (`{id, type, text}`), where `type` is one of ten elements: the six screenplay basics (heading, action, character, parenthetical, dialogue, transition) plus shot, act (act breaks), lyrics and note. `SPEECH` in `screenplay/types.ts` lists the types printed under a cue without a blank line, and `prints()` is false for notes, which every count, the print copy and the sheets leave out. `readBlocks` reads a type it doesn't know as action, so a script written by a newer build survives an older tab's save. The editor loads a document once with `get()` (it doesn't use `onValue`, so remote updates can't overwrite what you're typing). It first draws the copy remembered in `misc/seen.ts`, if any, and autosave waits until the fresh copy has arrived; if the two differ, the fresh one replaces the page and autosaves after a debounce through `saveDocumentContent`, then `touchParents` bumps the `lastUpdated` of the project and folder that hold it (the editor loads those parents in an effect keyed on the document's `projectId`, so moving the document reloads them), so home and the folder page sort by writing activity. The logic has no UI dependencies: the element flow, character suggestions, page estimates and Fountain export are in `@storia/core/screenplay/` (shared with mobile), and the importers stay in web-new's `src/screenplay/`, since they need browser APIs. In all: the element flow for Enter/Tab/Backspace, character suggestions, page estimates, Fountain export, and import from Final Draft (`finalDraft.ts`, .fdx XML) and WriterDuet (`writerDuet.ts`, used by the New document dialog). A .wdz is a ZIP (read by `misc/unzip.ts`) holding `script.json`, which stores no text, only each draft's edit history; the reader replays it, with undo and redo kept per line. The UI is in `components/screenplay/` and `views/DocumentView.tsx`. The editor (`components/screenplay/ScriptEditor.tsx`) runs on ProseMirror: the script is one document, one node type per element, so selection, undo and find run across the whole script. Its pieces live in `src/screenplay/editor/`: the schema, the converters between `ScriptBlock[]` and the document (unchanged blocks keep their objects), the plugin that keeps block ids unique, the keys and typing rules (built on `flow.ts`), placeholders, and the plain-text clipboard (Fountain out, action in). Changes the rest of the screen asks for (the element menu, New scene) go through the editor's handle as edits it can undo; only a different script coming down rebuilds the document. Page layout uses `ch` units of 12pt Courier, so indents match industry margins and the whole page scales as one unit. Printing uses a separate static copy (`PrintScript`) and the `@media print` rules in `screenplay.css`.

**Boards:** each project can have one board (`views/BoardView.tsx`), for planning the story on cards. It holds `cards` (in story order, each `{id, title, text, body?, act?, groups?, scenes?, characters?, values?}`), `groups` (`{id, name}`), `properties` (the board's own fields, `{id, name, type, options?}`, of a fixed type: select, multi, text, number, date or checkbox; a card's `values` are kept to fit them by `fitValue`) and `acts` (`{id, name}`, in order: the board's own, which a draft's act breaks can fill in through `actsInScript`, so the plan doesn't change when a draft does), stored apart from the project at `boards/{projectId}` with an `owner`, so the project page's subscription doesn't carry every card. The logic is pure and lives in `@storia/core/board/board` (`packages/core/src/board/board.ts`): `readBoard` turns whatever the database holds into a board, and every change (add, edit, move or remove a card; add, rename or remove a group, which keeps its cards) is a function from one board to the next. The card list is always kept act by act, cards in no act first (`inActOrder`), so numbers read straight down the board; a card changes act or place only through `placeCard`. `changeBoard` writes every part of the board, so a new part must be added there too. A card opens as a page (`views/CardView.tsx`, or `CardPeek`, a side peek over the editor), both drawing `components/board/CardDocument.tsx`: the title and the body autosave after a pause, the detail rows (act, place, groups, `ScriptLinks`, `PropertyRows`) write at once. The body (`board/body.ts`) is a small ProseMirror document stored as its JSON beside a plain-text copy in `text` (which tiles and older tabs read); write it through `bodyJSON`, since ProseMirror's attribute objects have no prototype and Firebase rejects them. A scene link is `{doc, scene}`, the draft's id and the scene's heading block id; `board/scripts.ts` loads the project's drafts for them, and the editor opens at a scene passed in the route's state (`{scene}`). `useBoardScreen` loads the project, folder and board for the board screens. `changeBoard` applies one inside `runTransaction`, so it lands on the latest copy and two tabs don't undo each other. A missing board reads as an empty one, so the read rule allows it for the project's owner. Groups are neutral tags and never colour-coded (the Revision Paper Rule). The dialogs are in `components/board/`; it sits among the project's documents without being one: a sheet on the project shelf after the drafts, and the Board view of the editor's project rail (`components/board/BoardRail.tsx`, which edits it there, through the same dialog), both read from the same `boards/` path, so it never takes a revision colour or counts as a draft.

**Auth/session:** login uses Firebase Auth email/password. The app tracks the session through the `sessionStorage` keys `"Auth Token"` and `"User ID"`, which views read directly. `main.tsx` waits for `auth.authStateReady()` before rendering, so database reads go out authenticated. At the same point it syncs `sessionStorage` with the Firebase user: it restores the session in new tabs and clears it when Firebase has signed the user out. Logging out (`logOut` in `misc/session.ts`) signs out of Firebase and clears `sessionStorage`.

**State and routing:** there is no state library. `App.tsx` defines every route (`/`, which redirects to Log in, `account/login|create|logout`, `terms-of-service`, `privacy-policy`, `home`, `folder/:id`, `project/:id`, `project/:id/board`, `project/:id/board/:cardId`, `document/:id`) and owns the shared UI state: the error the create dialogs show inline, and the sidebar toggle (persisted in `localStorage` under `sidebarVisible`). It passes this state down as props, and views take the `PropsWithSidebar` type exported from `views/Home.tsx`. A new top-level view needs to be registered in `App.tsx` and wired up with these props. `home`, `folder/:id`, `project/:id`, `project/:id/board` and `project/:id/board/:cardId` sit under the `Shell` layout route (`components/Shell.tsx`), which owns the page frame, the folder rail (`Sidebar`, with New folder and the account menu at its foot) and the New folder and Settings dialogs, and keeps them mounted between those screens, so those views render only their content (dialogs, `main`, `Loading` or `LoadError`), with no `Sidebar` or full-screen wrapper of their own. Shell also keeps the previous screen up until the next one is ready: `Loading` holds its screen while it is mounted (`useHoldScreen` in `misc/screenHold.ts`), and once the next screen has no spinner left, or after 300ms, it replaces the previous one outright.

**Styling:** every screen follows `DESIGN.md` (light only). The app's world is Revision Pages: each document wears the industry revision colour for its place in the project (white, blue, pink, yellow… by creation order, from `src/screenplay/revisions.ts`), that paper is the only colour, and the interface is set in Figtree with ink (#1B1B1F) for text, the primary button and focus. A surface joins the world by putting `sw sw-rev` on its root; the tokens (`--rail`, `--ui`, `--muted`, `--hair`, `--wash`, `--paper`, `--signal` and so on) and the shared classes (`sw-button`, `sw-button-soft` (the ink primary), `sw-input`, `sw-label`, `sw-icon`, `sw-card`, `sw-band`, `sw-rev-chip`, `sw-rev-strip`, `sw-stack`, `sw-sheet`, `sw-rail`, `sw-dialog`, `sw-spinner` and others) live in `src/screenplay/world.css`. Every screen, the signed-out ones included, carries both classes: the tokens sit on `.sw`, and the `.sw-rev` rules refine the shared classes. Tailwind handles layout and reads the tokens with arbitrary values like `text-[color:var(--muted)]`; Tailwind has no custom colours or dark mode. Text outside the script uses Tailwind's standard sizes (`text-sm` and up; `text-xs` only for the editor's dense rail meta), never arbitrary ones like `text-[13px]`; the script page and the project sheets' miniature Courier keep exact sizes for screenplay metrics. Icons are drawn strokes from `components/screenplay/StrokeIcon.tsx`. Signed-out screens wrap their content in `AuthCard` (`components/AuthCard.tsx`), and the form helpers (`FieldError`, `readForm`, `useEscape`) are in `misc/forms.ts`. Page titles are set with `useTitle` from `misc/title.tsx`.
